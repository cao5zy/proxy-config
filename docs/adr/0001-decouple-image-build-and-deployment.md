# ADR-0001：解耦镜像构建与站点部署

- 状态：已接受
- 日期：2026-09-04

## 背景

当前 `micro_proxy start` 会扫描 `scan_dirs`、根据目录内容变化构建 `<app>:latest`、生成配置，并执行 `docker compose down` 后再 `up -d`。这会将耗时的 Rust 等项目构建与线上切换绑定在一起。新版本构建或运行失败时，旧容器已经停止；回退又需要检出旧源码并重新构建，导致故障版本可能长期暴露，或站点长时间不可用。

固定的 `latest` 标签还是可变引用：它不能可靠地表达当前运行的是哪个构建产物，也无法保证回滚到完全相同的镜像。

## 决策

1. 构建与部署分为独立操作。`micro_proxy build [APP...]` 只产生镜像并登记候选版本；绝不改变正在运行的容器、Nginx 配置、流量或宿主机卷数据。特别是，构建不得执行卷权限初始化脚本（包括 `chown`）。
2. 每次构建使用不可变镜像引用，格式为 `<app>:sha-<短哈希>`。标签对应唯一构建输入，`latest` 不再作为部署依据。
3. 保留 `micro_proxy start`，但其职责变为按部署状态启动已选择的活动镜像；它不再依据源码变化构建镜像。
4. 使用 `micro_proxy deploy <APP> --image <IMAGE>` 明确选择待运行的已构建镜像；部署状态记录 `active_image` 与 `previous_image`。
5. 使用 `micro_proxy rollback <APP>` 将活动版本切回 `previous_image`，不依赖源码、不触发构建。
6. 容器名称继续来自 `micro-app.yml`，不是 `start` 或 `deploy` 的位置参数。容器名描述运行实例；镜像引用描述构建产物，二者不能混用。
7. 兼容既有配置。首次升级发现旧的 `<app>:latest` 时，或 `build` 已仅写入候选镜像但尚无活动部署时，将该镜像及既有容器登记为活动版本；用户无需修改 `proxy-config.yml`、`micro-app.yml` 或 `micro-app.volumes.yml`。
8. 卷权限初始化属于部署前置步骤：`deploy` 仅针对目标应用、在启动候选容器前执行其 `micro-app.volumes.yml` 中声明的权限脚本。该配置可能修改宿主机卷目录，使用者应仅在确有需要时配置，且对已有数据目录显式评估 `recursive` 的影响。

第一期的部署仍可能重建目标应用的容器，因而存在短暂切换窗口；它不承诺零停机。第二期采用蓝绿部署：先启动并验证候选容器，Nginx 切流成功后才停止旧容器。

## 备选方案

### 继续使用 `latest`

拒绝。该标签会被新构建覆盖，不能作为可靠的版本标识，也无法在源码改变后保证回滚至原来的镜像。

### 使用 `micro_proxy start [容器名称] [镜像名称]`

拒绝。容器名已是微应用配置的一部分，允许命令行覆盖会造成配置与实际运行状态脱节；镜像选择应是显式部署操作。

### 只新增 `build`，保留原 `start` 的自动构建逻辑

拒绝。这仍允许普通启动操作隐式构建并替换线上版本，没有解除核心风险。

## 后果

正面影响：构建可在站点持续运行时完成且不会触碰宿主机卷数据；上线的镜像可追溯；回滚不再需要恢复源码和重新编译；现有应用配置不需要迁移。

代价：需要新增部署状态、镜像保留与清理策略，并引入 `build`、`deploy`、`rollback` 命令。第一期切换仍会有短暂中断；第二期需要候选容器、健康检查和 Nginx 平滑切流实现零/近零停机。
